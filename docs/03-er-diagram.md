# ER Diagram — 개체-관계 다이어그램 및 데이터 사전

프로젝트: 학꾸(Hakku) · 작성일: 2026-06-25 · 버전 1.0

---

## 1. 개요

### 1.1 데이터베이스 구성

학꾸 플랫폼은 단일 **PostgreSQL 16** 인스턴스의 `hakku` 데이터베이스 하나를 두 개의 서비스가 공유하는 구조를 채택한다. 물리적으로는 동일한 데이터베이스이지만, 스키마 변경 이력(마이그레이션)은 서비스별로 완전히 분리하여 각 서비스의 배포 독립성을 보장한다.

| 구분 | 소유 서비스 | 테이블 수 | Flyway 이력 테이블 | Flyway 버전 범위 | 마이그레이션 책임 |
|---|---|---|---|---|---|
| main DB 영역 | main-server (Spring Data JDBC) | 18 | `flyway_schema_history` | V1 ~ V19 | 회원·인증·커뮤니티·매거진·상품·주문·추천·알림 |
| payment DB 영역 | payment-server (JPA) | 2 | `flyway_schema_history_payment` (baseline 0) | V1 ~ V2 | 토스페이먼츠 결제·Outbox 이벤트 |
| **합계** | — | **20** | — | — | — |

- 두 서비스는 같은 `hakku` 데이터베이스에 접속하지만, 서로의 테이블에 대한 물리적 외래키(FK)를 설정하지 않는다. payment-server가 참조하는 `user_id`·`reference_id`는 **논리적 참조(cross-module logical reference)** 로만 존재하며, 무결성은 애플리케이션 계층에서 보장한다.
- Flyway 이력 테이블을 분리(`flyway_schema_history_payment`, baseline 0)함으로써 두 서비스의 마이그레이션이 서로의 버전 번호 충돌이나 잠금 경합 없이 독립적으로 진행된다.

### 1.2 명명 규칙 (Naming Convention)

| 대상 | 규칙 | 예시 |
|---|---|---|
| 테이블명 | 소문자 snake_case, 복수형 | `users`, `cart_items`, `payment_outbox` |
| 컬럼명 | 소문자 snake_case | `personal_color`, `idempotency_key` |
| 기본키 | 단일 surrogate 키는 `id` (단, 순수 연관 테이블은 복합 PK) | `id`, `(user_id, style)` |
| 외래키 | `{참조엔티티 단수}_id` | `user_id`, `product_id`, `author_id` |
| 자기참조 FK | 의미를 드러내는 접두사 + `_id` | `follower_id`, `following_id` |
| 시각 컬럼 | `_at` 접미사, `TIMESTAMPTZ` | `created_at`, `updated_at`, `sent_at` |
| 불리언 컬럼 | 상태 형용사 또는 과거분사 | `active`, `published`, `onboarding_completed` |

### 1.3 데이터 타입 규칙 (Type Convention)

| 의미 범주 | 채택 타입 | 비고 |
|---|---|---|
| 식별자(PK/FK) | `BIGINT` | main DB 18개 테이블은 모두 `id BIGINT GENERATED BY DEFAULT AS IDENTITY` PK |
| 금액(원화) | `BIGINT` | `price`, `amount`, `total_amount`, `line_total` 등은 원 단위 정수. 소수점/통화 분리 미사용 |
| 수량·순서·재시도 | `INT` | `quantity`, `sort_order`, `display_order`, `retry_count`, `version` |
| ENUM 값 | `VARCHAR` (문자열) | 네이티브 PostgreSQL ENUM 타입이 아닌 **문자열로 영속화**하고 애플리케이션 계층에서 검증·파싱. `role`, `status`, `board`, `personal_color`, `diagnosis_status` 등 모두 VARCHAR |
| 짧은 텍스트 | `VARCHAR` | 이메일·닉네임·이름·키워드 등 |
| 긴 텍스트/마크다운 | `TEXT` | `content`, 매거진 본문 |
| URL | `TEXT` | `image_url`, `profile_image_url`, `cover_image_url`, `purchase_url` |
| 시각 | `TIMESTAMPTZ` | 타임존 인식 타임스탬프 |
| 참/거짓 | `BOOLEAN` | — |

> 규칙 주석: ENUM을 VARCHAR로 보관하는 이유는 (1) Flyway 마이그레이션에서 ENUM 멤버 추가 시 `ALTER TYPE` 잠금 비용을 회피하고, (2) Spring Data JDBC / JPA 양쪽에서 매핑이 단순하기 때문이다. 허용 값 검증은 도메인 계층의 enum 변환에서 수행한다.

### 1.4 역사적 주석 — `curation_cards` (최종 스키마 제외)

`curation_cards` 테이블은 Flyway **V14에서 생성**되었으나 **V18에서 삭제(DROP)** 되어 **최종 누적 스키마에는 존재하지 않는다.** 따라서 본 데이터 사전(아래 §3)과 ER 다이어그램(§2)에서는 제외하며, 본 항목은 스키마 진화 이력을 추적하기 위한 역사적 기록으로만 남긴다. 최종 스키마의 진실의 원천은 Flyway `V1~V19`(main) 및 `payment V1~V2`의 누적 결과이며, 총 테이블 수는 20개이다.

## 2. ER 다이어그램

아래 다이어그램은 main DB 18개 테이블과 payment DB 2개 테이블, 그리고 그 사이의 관계(실선=물리 FK, 점선=논리 참조/스냅샷)를 표현한다. 통합 HTML 빌드는 아래 도메인별 D2 다이어그램을 SVG로 렌더링한다.

**도메인 A — 회원 · 소셜 · 커뮤니티** (8개 테이블)

```d2
direction: right
users: "users · 회원" {
  shape: sql_table
  id: bigint {constraint: primary_key}
  email: varchar(255) {constraint: unique}
  nickname: varchar(255)
  role: varchar(20)
  personal_color: varchar(40)
  diagnosis_status: varchar(20)
  onboarding_completed: boolean
}
ups: "user_preferred_styles" {
  shape: sql_table
  user_id: bigint {constraint: foreign_key}
  "style": varchar(100) {constraint: primary_key}
}
upc: "user_preferred_colors" {
  shape: sql_table
  user_id: bigint {constraint: foreign_key}
  "color": varchar(40) {constraint: primary_key}
}
follows: "follows · 팔로우" {
  shape: sql_table
  id: bigint {constraint: primary_key}
  follower_id: bigint {constraint: foreign_key}
  following_id: bigint {constraint: foreign_key}
}
posts: "posts · 게시글" {
  shape: sql_table
  id: bigint {constraint: primary_key}
  author_id: bigint {constraint: foreign_key}
  title: varchar(255)
  board: varchar(32)
  image_url: text
}
comments: "comments · 댓글" {
  shape: sql_table
  id: bigint {constraint: primary_key}
  post_id: bigint {constraint: foreign_key}
  author_id: bigint {constraint: foreign_key}
}
post_likes: "post_likes · 좋아요" {
  shape: sql_table
  id: bigint {constraint: primary_key}
  post_id: bigint {constraint: foreign_key}
  user_id: bigint {constraint: foreign_key}
}
post_products: "post_products · 연관상품" {
  shape: sql_table
  id: bigint {constraint: primary_key}
  post_id: bigint {constraint: foreign_key}
  product_id: bigint {constraint: foreign_key}
}
users.id -> ups.user_id
users.id -> upc.user_id
users.id -> follows.follower_id: follower
users.id -> follows.following_id: following
users.id -> posts.author_id: 작성
users.id -> comments.author_id
users.id -> post_likes.user_id
posts.id -> comments.post_id
posts.id -> post_likes.post_id
posts.id -> post_products.post_id
```

> 그림 3-1a. 회원·소셜·커뮤니티 도메인. `post_products.product_id` 는 커머스 도메인의 `products` 를 참조한다.

```d2

reviews: "reviews · 리뷰" {
  shape: sql_table
  id: bigint {constraint: primary_key}

wish: "wishlists · 찜" {

wlikes: "wishlist_likes · 찜좋아요" {
  shape: sql_table
  id: bigint {constraint: primary_key}

oitems: "order_items · 주문항목(스냅샷)" {

users.id -> reviews.author_id
users.id -> wish.user_id
users.id -> wlikes.user_id
users.id -> orders.user_id
products.id -> pstyles.product_id
products.id -> pcolors.product_id
products.id -> cart.product_id
products.id -> reviews.product_id
products.id -> wish.product_id
wish.id -> wlikes.wishlist_id
orders.id -> oitems.order_id
products.id -> oitems.product_id: 스냅샷(FK없음) {style.stroke-dash: 4}
```

**도메인 C — 결제 · 콘텐츠** (3개 테이블)

```d2
direction: right
payments: "payments · 결제 (payment-server)" {
  shape: sql_table
  id: bigint {constraint: primary_key}
  user_id: bigint
  reference_type: varchar(255)
  reference_id: varchar(255)
  idempotency_key: varchar(255) {constraint: unique}
  amount: bigint
  status: varchar(255)
  version: bigint
}
outbox: "payment_outbox · 아웃박스" {
  shape: sql_table
  id: bigint {constraint: primary_key}
  aggregate_type: varchar(255)
  aggregate_id: bigint
  event_type: varchar(255)
  status: varchar(255)
  retry_count: integer
}
magazines: "magazines · 매거진 (콘텐츠)" {
  shape: sql_table
  id: bigint {constraint: primary_key}
  title: varchar(200)
  content: text
  display_order: integer
  published: boolean
}
users: "users (논리참조)" { shape: sql_table; id: bigint {constraint: primary_key} }
orders: "orders (논리참조)" { shape: sql_table; id: bigint {constraint: primary_key} }
users.id -> payments.user_id: 논리참조 {style.stroke-dash: 4}
orders.id -> payments.reference_id: reference {style.stroke-dash: 4}
payments.id -> outbox.aggregate_id: outbox(논리) {style.stroke-dash: 4}
```

> 그림 3-1c. 결제(payment-server)·콘텐츠 도메인. `payments.user_id`/`reference_id` 는 물리 FK 없는 논리 참조(점선)다.

**그림 3-1. 학꾸 ER 다이어그램**

> 다이어그램 표기 범례: 실선(`||--o{`)은 물리적 외래키(FK) 1:N 관계, 점선(`|o..o{`, `||..o{`)은 물리 FK 없이 애플리케이션이 관리하는 논리 참조 또는 스냅샷 관계를 나타낸다. 위 다이어그램의 각 엔티티는 가독성을 위해 핵심 컬럼만 표기했으며, 전체 컬럼·제약은 아래 §3 데이터 사전을 정본으로 한다.

## 3. 데이터 사전 (Data Dictionary)

main DB 18개 테이블 + payment DB 2개 테이블, 총 20개 테이블의 전체 컬럼·제약을 정의한다. 모든 main DB 테이블은 별도 명시가 없는 한 `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` 와 `created_at`/`updated_at TIMESTAMPTZ` 를 가진다(단, 순수 연관 테이블은 복합 PK이며 일부는 `created_at`만 보유).

### 3.1 users — 회원

| 컬럼명 | 데이터타입 | 제약 | 설명 |
|---|---|---|---|
| id | BIGINT | PK, IDENTITY | 회원 식별자 |
| email | VARCHAR | UK, NOT NULL | 로그인 이메일(고유) |
| nickname | VARCHAR | NOT NULL | 표시용 닉네임 |
| password_hash | VARCHAR | — | 비밀번호 해시(소셜/시스템 계정은 null 가능) |
| role | VARCHAR | NOT NULL | 권한 ENUM: `NORMAL` \| `SELLER` \| `ADMIN` |
| personal_color | VARCHAR | nullable | 진단된 16종 퍼스널컬러 ENUM(진단 전 null) |
| profile_image_url | TEXT | — | 프로필 이미지 URL |
| diagnosis_status | VARCHAR | NOT NULL, DEFAULT `NONE` | 진단 상태 ENUM: `NONE` \| `PENDING` \| `COMPLETED` |
| diagnosis_image_url | TEXT | — | 진단 결과 이미지 URL(storage result) |
| onboarding_completed | BOOLEAN | NOT NULL, DEFAULT `false` | 온보딩 완료 여부(NORMAL 필수 게이트) |
| created_at | TIMESTAMPTZ | NOT NULL | 가입 시각 |

### 3.2 user_preferred_styles — 회원 선호 스타일 (M:N 연관)

| 컬럼명 | 데이터타입 | 제약 | 설명 |
|---|---|---|---|
| user_id | BIGINT | PK, FK→users(id) ON DELETE CASCADE | 회원 식별자 |
| style | VARCHAR | PK | 선호 스타일 키워드 |

> 복합 PK `(user_id, style)`. surrogate `id` 없음 — 순수 연관 테이블.

### 3.3 user_preferred_colors — 회원 선호 컬러 (M:N 연관)

| 컬럼명 | 데이터타입 | 제약 | 설명 |
|---|---|---|---|
| user_id | BIGINT | PK, FK→users(id) ON DELETE CASCADE | 회원 식별자 |
| color | VARCHAR | PK | 선호 컬러 키워드 |

> 복합 PK `(user_id, color)`. surrogate `id` 없음 — 순수 연관 테이블.

### 3.4 posts — 커뮤니티 게시글

| 컬럼명 | 데이터타입 | 제약 | 설명 |
|---|---|---|---|
| id | BIGINT | PK, IDENTITY | 게시글 식별자 |
| author_id | BIGINT | FK→users(id) ON DELETE CASCADE, NOT NULL | 작성자 |
| title | VARCHAR | NOT NULL | 제목 |
| content | TEXT | NOT NULL | 본문 |
| board | VARCHAR | NOT NULL, DEFAULT `GENERAL` | 게시판 ENUM: `GENERAL` \| `STUDENT_ID` |
| image_url | TEXT | — | 첨부 이미지 URL |
| created_at | TIMESTAMPTZ | NOT NULL | 작성 시각 |
| updated_at | TIMESTAMPTZ | NOT NULL | 수정 시각 |

### 3.5 comments — 댓글

| 컬럼명 | 데이터타입 | 제약 | 설명 |
|---|---|---|---|
| id | BIGINT | PK, IDENTITY | 댓글 식별자 |
| post_id | BIGINT | FK→posts(id) ON DELETE CASCADE, NOT NULL | 대상 게시글 |
| author_id | BIGINT | FK→users(id) ON DELETE CASCADE, NOT NULL | 작성자 |
| content | TEXT | NOT NULL | 댓글 내용 |
| created_at | TIMESTAMPTZ | NOT NULL | 작성 시각 |

### 3.6 post_likes — 게시글 좋아요

| 컬럼명 | 데이터타입 | 제약 | 설명 |
|---|---|---|---|
| id | BIGINT | PK, IDENTITY | 좋아요 식별자 |
| post_id | BIGINT | FK→posts(id) ON DELETE CASCADE, NOT NULL | 대상 게시글 |
| user_id | BIGINT | FK→users(id) ON DELETE CASCADE, NOT NULL | 좋아요 누른 회원 |
| created_at | TIMESTAMPTZ | NOT NULL | 좋아요 시각 |

> UK `(post_id, user_id)` — 한 회원당 게시글 1회 좋아요. 고유성은 PK가 아닌 UK로 보장.

### 3.7 post_products — 게시글 연관 상품 (학생증 자랑) (M:N 연관)

| 컬럼명 | 데이터타입 | 제약 | 설명 |
|---|---|---|---|
| id | BIGINT | PK, IDENTITY | 연관 식별자 |
| post_id | BIGINT | FK→posts(id) ON DELETE CASCADE, NOT NULL | 대상 게시글 |
| product_id | BIGINT | FK→products(id) ON DELETE CASCADE, NOT NULL | 연관 상품 |
| sort_order | INT | NOT NULL, DEFAULT `0` | 게시글 내 노출 순서 |
| created_at | TIMESTAMPTZ | NOT NULL | 등록 시각 |

> UK `(post_id, product_id)`. posts↔products를 잇는 M:N 중간 테이블(surrogate id 보유).

### 3.9 product_styles — 상품 스타일 (M:N 연관)

## 4. 관계 정의

### 4.1 1:N 관계 (물리 FK, 실선)

| 부모(1) | 자식(N) | FK 컬럼 | 의미 |
|---|---|---|---|
| users | products | seller_id | 한 판매자가 여러 상품을 등록 |
| users | posts | author_id | 한 회원이 여러 게시글 작성 |
| users | comments | author_id | 한 회원이 여러 댓글 작성 |
| users | post_likes | user_id | 한 회원이 여러 게시글에 좋아요 |
| users | cart_items | user_id | 한 회원이 여러 장바구니 항목 보유 |
| users | reviews | author_id | 한 회원이 여러 리뷰 작성 |
| users | orders | user_id | 한 회원이 여러 주문 |
| users | wishlists | user_id | 한 회원이 여러 상품 찜 |
| users | wishlist_likes | user_id | 한 회원이 여러 찜에 좋아요 |
| posts | comments | post_id | 한 게시글에 여러 댓글 |
| posts | post_likes | post_id | 한 게시글에 여러 좋아요 |
| products | cart_items | product_id | 한 상품이 여러 장바구니에 담김 |
| products | reviews | product_id | 한 상품에 여러 리뷰 |
| products | wishlists | product_id | 한 상품이 여러 회원에게 찜됨 |
| wishlists | wishlist_likes | wishlist_id | 한 찜에 여러 좋아요 |
| orders | order_items | order_id | 한 주문에 여러 주문 항목 |
| payments | payment_outbox | (aggregate_id 논리) | 한 결제가 여러 아웃박스 이벤트 생성 |

### 4.2 자기참조 1:N (follows)

`users`는 `follows` 테이블을 통해 자기 자신과 M:N 관계를 형성한다. `follower_id`(팔로우 주체)와 `following_id`(팔로우 대상) 두 FK가 모두 `users(id)`를 가리킨다. CHECK 제약 `(follower_id <> following_id)`로 자기 자신 팔로우를 금지하고, UK `(follower_id, following_id)`로 중복 팔로우를 방지한다.

### 4.3 M:N 관계와 중간 테이블

| M:N 관계 | 중간 테이블 | 키 구조 | 비고 |
|---|---|---|---|
| users ↔ 선호 스타일 | user_preferred_styles | 복합 PK `(user_id, style)` | 순수 연관(surrogate id 없음) |
| users ↔ 선호 컬러 | user_preferred_colors | 복합 PK `(user_id, color)` | 순수 연관(surrogate id 없음) |
| products ↔ 스타일 | product_styles | 복합 PK `(product_id, style)` | 순수 연관(surrogate id 없음) |
| products ↔ 컬러 | product_colors | 복합 PK `(product_id, color)` | 순수 연관(surrogate id 없음) |
| posts ↔ products | post_products | surrogate `id` PK + UK `(post_id, product_id)` | 부가 속성(sort_order) 보유, 학생증 자랑 연관상품 |

> 4개 선호/속성 테이블은 부가 컬럼이 없는 순수 연관이므로 복합 PK를 채택했고, `post_products`는 노출 순서(`sort_order`)라는 부가 속성을 가지므로 surrogate id + UK 조합을 채택했다.

### 4.4 논리 참조 (물리 FK 없음, 점선)

크로스모듈 경계 또는 이력 보존 목적상 의도적으로 물리 FK를 두지 않은 참조이다. 무결성은 애플리케이션 계층에서 보장한다.

| 참조 컬럼 | 가리키는 대상 | 사유 |
|---|---|---|
| order_items.product_id | products(id) | **주문 시점 스냅샷** — 상품 변경/삭제가 주문 이력에 영향 주지 않도록 FK 미설정 |
| payments.user_id | users(id) | **크로스모듈**(payment-server ↔ main DB) — 서비스 독립 배포를 위해 물리 FK 미설정 |
| payments.reference_id | orders(id) 등 | **크로스모듈 + 다형 참조**(reference_type에 따라 대상 가변) |
| payment_outbox.aggregate_id | payments(id) 등 | 아웃박스 패턴의 논리 애그리거트 참조 |

### 4.5 ON DELETE 정책

| 관계 유형 | ON DELETE 정책 | 비고 |
|---|---|---|
| users → 자식(products, posts, comments, post_likes, cart_items, reviews, orders, wishlists, wishlist_likes, follows, user_preferred_*) | CASCADE | 회원 삭제 시 종속 데이터 함께 삭제 |
| posts → comments, post_likes, post_products | CASCADE | 게시글 삭제 시 종속 데이터 함께 삭제 |
| products → cart_items, reviews, wishlists, product_styles, product_colors, post_products | CASCADE | 상품 삭제 시 종속 데이터 함께 삭제 |
| wishlists → wishlist_likes | CASCADE | 찜 삭제 시 좋아요 함께 삭제 |
| orders → order_items | CASCADE | 주문 삭제 시 항목 함께 삭제 |
| order_items.product_id → products | (없음) | 스냅샷 — 물리 FK 없어 DB 차원 cascade 없음, 이력 보존 |
| payments.user_id / reference_id → main DB | (없음) | 크로스모듈 논리 참조 — DB cascade 없음, 애플리케이션 관리 |
| payment_outbox.aggregate_id → payments | (없음) | 논리 참조 — DB cascade 없음 |

| STUDENT_ID | 학생증 자랑 게시판(연관 상품 임베드) |

### 5.8 PersonalColorType — 퍼스널컬러 16종 (users.personal_color)

4계절 × 4톤 = 16종. 추천 점수 산정 시에는 계절 단위(봄/여름/가을/겨울)로 환원하여 사용한다.

| 계절 | 톤 1 | 톤 2 | 톤 3 | 톤 4 |
|---|---|---|---|---|
| 봄 (Spring) | LIGHT_SPRING | TRUE_SPRING | BRIGHT_SPRING | CLEAR_SPRING |
| 여름 (Summer) | LIGHT_SUMMER | TRUE_SUMMER | SOFT_SUMMER | COOL_SUMMER |
| 가을 (Autumn) | SOFT_AUTUMN | TRUE_AUTUMN | DEEP_AUTUMN | MUTED_AUTUMN |
| 겨울 (Winter) | BRIGHT_WINTER | TRUE_WINTER | DEEP_WINTER | CLEAR_WINTER |

## 6. 비관계형 저장소 (부록)

관계형 스키마 외에, 실시간성·휘발성·고빈도 접근이 요구되는 데이터는 **Redis 7**에 저장한다. 아래는 ER 모델의 부록으로서 Redis 키 구조를 정의한다.

| 키 패턴 | 자료구조 | 용도 | 정책 |
|---|---|---|---|
| `user:{id}:notifications` | List | 알림함 — Kafka `notification.created` 소비 결과 적재, 프론트 폴링 조회 | 최대 50개 유지(초과 시 오래된 항목 trim) |
| `user:{id}:recent-actions` | List | 최근 행동로그(클릭·찜·장바구니) — 추천 점수 산정 입력 | 행동 이력 누적 |
| `chat:history:{user_id}` | Sorted Set | 챗봇 대화 기억 — score=타임스탬프 | 1시간 슬라이딩 윈도우(만료 외 항목 제거) |
| `jwt:blacklist:{token}` | String(Key) | 로그아웃·폐기된 JWT 차단 목록 | 토큰 만료 시점까지 TTL |
| `product:{id}:cache` | String/Hash | 상품 조회 캐시(읽기 부하 완화) | 갱신 시 무효화, TTL 기반 |

> 위 Redis 구조는 관계형 무결성 제약(FK/UK)의 대상이 아니며, 데이터 생애주기는 TTL·trim·윈도우 정책으로 관리된다. 알림·행동로그·챗봇 기억·JWT 블랙리스트·상품 캐시는 각각 §3의 정규 테이블을 보완하는 휘발성/파생 데이터이다.
